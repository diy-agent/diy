# 角色（BotRole）：从「每个容器一个 bot」到「类型级席位」

> 2026-11-24 定稿并落地（task-mwlxxv3u）。此前设计推理见 journal 的 11-22 三条与
> `2026-11-13-room-model.md`；本文件是**做完之后**的口径：为什么这么切、迁移怎么走、
> 哪些语义跟着变了。

## 一句话

**Bot 概念废弃，改为 BotRole**：角色是某种工作对象类型（project / task / 任意插件类型）上的
**固定席位**，全局一张表；房间里「有谁」不再是存下来的关系，而是**按房间类型派生**出来的。

## 为什么（真库的证词）

| 观察 | 数 |
|---|---|
| `bots` 行与容器数 | 35 行 / 35 个容器，**1:1 同名** |
| task 侧 persona 完全相同的行 | 27 个 |
| 被复用到第二个房间的 bot | 0 |

「全局身份」既没被复用，又要每建一个容器就复制一份 —— 于是：

- 改一次人格要改 27 份，漏一份就有一间房的助手口径不一样；
- 新建任务要先造 bot 再 `addMember`，两个动作必须都成功，否则那间房零成员、发消息没人应答；
- 「这个 bot 属于哪间房」（`home_entity_id`）是个假概念，它只是「在哪建的」。

## 数据

```sql
CREATE TABLE bot_roles (
    id TEXT PRIMARY KEY,
    type TEXT NOT NULL,               -- 归属类型：与 Room.type 同一个词表（开放字符串）
    name TEXT NOT NULL,
    color TEXT NOT NULL,
    instructions TEXT NOT NULL DEFAULT '',  -- 原 persona：拼进系统提示词
    primary_flag INTEGER NOT NULL DEFAULT 0,
    model_key TEXT,                   -- null = 继承房间 → 全局默认
    reasoning_effort TEXT,            -- null = 用模型/服务商缺省
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX bot_roles_primary ON bot_roles(type) WHERE primary_flag = 1;
CREATE INDEX bot_roles_type ON bot_roles(type, created_at);
```

两条护栏都在库里，不靠应用层自觉：

- **每类型至多一个 `primary`**：唯一索引 + `upsertRole` 先撤同类型别人的旗（一次漏写 = 一段时间双应答）；
- **每类型至少留一个角色**：服务端在 `roles.remove` 里拦（成员是派生的，删光了那类房间永远没人应答）。

会话键 `session_state` 的列从 `bot_id` 改名为 `bot_role_id`（表里装的一直是「谁在这个房间里」，
只是现在那个 id 指向角色）；老库由 `ALTER TABLE … RENAME COLUMN` 改过来，主键随之更新。

## 派生：房间里「有谁」

唯一实现点 `protocol/room.ts`：

```ts
membersOfType(roles, type)  // type 相同的角色 → RoomMember[]
botOfRole(role)             // 角色 → 房间里的化身（persona ← instructions）
```

顺序 = **primary 排头，其余按 `createdAt` 早的在前，同刻用 id 兜底**。顺序不是装饰：
`primaryMemberOf` / 侧栏 / @ 补全都按「第一个成员」兜底，顺序一变默认应答就换人。

`room_members` 表**保留但不再是成员真源**：它只留作将来「实体级覆盖」（某间房单独加人 /
换人格）的落点，本期不做；`seed()` 每次启动都用派生结果盖写它。

## 跟着变的语义（都要知道，不然会当 bug 报）

1. **没有「把 bot 拉进房间」了**：`rooms.addMember` 与前端 `AddMemberDialog` 一起删掉。
   要往某类房间加人 ⇒ 去设置 → 角色，给那个类型建一个角色，该类**所有**房间同时生效。
2. **容器改名不再改助手名**：一个角色服务该类型所有房间，跟着某间房改名等于把别的房一起改了。
   任务标题与助手名字现在是两个独立概念（这也是角色页存在的意义）。
3. **新建房间零角色时自动补一个** `${type} 助手`：类型是开放字符串（`stock` 之类），
   不补的话那个房间零成员，用户还得先去角色页建人才能说话。
4. **改角色对已开会话的生效时机**：`RoomActor.refreshIdentities()` 把新身份推给已建好的
   session；已在跑的这一轮不重发（instructions 已经发出去了），从下一轮 / 下一条 item 生效。
5. **角色不是实体**：不再写 `entities` 行（老库的历史行由 `deleteRole` 顺手清）。

## 老库迁移（`db.ts` 的 `migrateBots`）

合并规则 = **同类型 + 同 persona = 同一个角色**（`type` 取 `home_entity_id` 的实体类型，
归属容器已不在时按 task 处理）：

| 字段 | 取法 |
|---|---|
| id | 组内**最早那行**的 bot id —— 单行组（几个项目 bot）的会话键因此一字不动 |
| name | 单行组用 bot 名；合并组用类型名（「任务助手」），否则 27 个任务会有一个叫「UI Workbench 架构对齐」的角色 |
| instructions | 组内 persona（相同才合得起来） |
| primary | 该类型里「组内在 room_members 当过 primary」次数最多的那组，平手取最早 |
| createdAt | 按旧行序单调递增（保证派生顺序与迁移前一致） |

会话 / 投递按新旧 id 映射重写；同一容器里两行撞到同一个角色时留 `to` 那条、丢 `from`（打日志）。
迁移完把旧表改名 `bots_v0` 留档（与 `rooms_v0` 一个路数，不删人数据）；新库根本不建 `bots`。

## 界面

- **角色页**：`/settings/roles`（设置页第二段）。左栏按类型分组，右栏是名字 / 颜色 / 人格 /
  默认应答 / 模型 / 推理强度。校验在出问题那根输入下面说（TanStack Form 字段级 validator）。
- **房间头**「角色」按钮 → 导航到角色页（房间头仍显示本房间的成员胶囊，它们来自派生）。
- 写面在 `entity-chat` 的 `roles.ts`（与 `modelConfig.ts` 同一套：写完 `refreshRoles()`，
  成员胶囊立刻跟上）；页面本体在 `apps/diy2/src/workbench/RolesView.tsx`。

## 没做的（明确留白）

- **实体级覆盖**：某间房单独换人格 / 塞一个额外成员。表结构留着（`room_members` 的
  `persona` / `model_key` 列），本期不写。
- **压缩槽位**（`uses.compact`）：11-22 的设计结论（压缩不是角色，是用途槽位）仍未进代码。
- **角色按房间模板预设**：新建项目时挑一个「项目角色组合」之类，属于上层玩法。
