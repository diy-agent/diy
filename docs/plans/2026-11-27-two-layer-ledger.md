## 三、定形：目标（顶层）→ 需求（一层子）

- **目标**（根）：一段独立、可以单独开始 / 完成 / 放弃的成果。**可以没有需求**，直接干。
- **需求**（子）：那个目标必须满足的一条可验收条件，`accept` 是它的必填内容（空 = 界面标「缺验收」）。
- **只有两层**：`parent` 只能指向顶层；需求下不再挂需求。真需要更细，就新建一个目标。
- **执行步骤不进账本**：改哪个文件、跑什么命令是 bot 自己的事，出处是 `journal` + `job` + 工具记录。

代码上：
- `UNIT_KINDS` / `UnitKind` / `UnitRecord.kind` 全删，写入不再带 `kind`（列保留 `DEFAULT 'need'`）。
- `UNIT_MAX_DEPTH = 1`；`unit_add` / `unit_update` 的 `parent` 越层直接报错（含同批循环、有子项换挂点）。
- 一个目标下需求 > 7 条：`unit_add` 回 `hint` 软提示（不硬拦 —— 硬拦会逼模型把不相干的需求塞进已有的几条）。
- `seq` 作用域从「任务内全局」改成「同一个父下」：目标之间排一次，每个目标下的需求各自再排。
- 迁移 `019-drop-unit-step`：把历史上 `kind <> 'need'` 的行归位成 `need`（生产 0 行；dev / 测试库可能有）。

## 四、为什么不是「无限树 + 深度校验」，也不拆两张表

- **无限树**：父子一旦成为主要组织方式，排序要绕开父节点、独立性说不清、模型会为了整理继续加父。
  真正的毛病是语义混乱，不是缩进太深。
- **两张表（`work_goals` + `work_requirements`）**：Goal 与 Requirement 的字段和生命周期几乎一样，
  拆了要写两遍迁移 / 事件 / RPC / UI 分支，而现有 153 条数据零迁移。**约束写在写入路径上就够**。
