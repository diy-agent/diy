# 作业（job）怎么让人看见 —— 内联卡片 + 「在跑」面板（2026-11-24）

用户 2026-11-24 在 lab 里连着说了四句，都是同一件事的不同侧面：

1. `job` 工具的输出要「像其他 bash 一样」：**先一行缩起的状态，点了才展开**；
2. 「运行中」这三个字**事后看**（翻历史消息）很容易误会成「现在还在跑」；
3. 「转到后台」「查状态」这类**看起来像按钮却点不动**的字样很误导 —— 重新规划；
4. 还需要一个方式：**看见当前在跑什么，并能取消**；先给几个 demo 挑形状。

1–3 是**已定口径**（不需要选），4 是**选型**（要挑）。

## 一、已定：内联卡片（`JobCard`）

改动都在 `pkgs.ts/ui/entity-chat/src/components/JobCard.tsx`，判据仍全在 chat-core 的 `jobOf`。

| 原来 | 现在 | 为什么 |
|---|---|---|
| 一摊到底：状态行 + 命令 + 目录 + 日志 + 尾部 | **默认一行**，点「›」展开全部明细 | 一条 `job wait` 能占半屏，九成时间只说明"等它结束"；工具调用的默认形态该是一行 |
| 一律写「运行中」 | 只有这一轮**真挂着它**（`entry.waiting`）才写「在跑」；历史里的写「没等到结束」 | 「运行中」是状态，不是历史；翻旧消息看到它必然误判 |
| 「转到后台」「查状态」做成圆角 chip | 降级成**展开后的一行灰字**：`这次：job 查状态` | 长得像按钮却点不动，是最贵的误会 |
| 结局埋在尾部 | 收起行里就有 `40.0s · 退出码 0` | 结束了 ≠ 成功了，结局要单列且立刻可见 |

`live` 由 surface 传：`entry.waiting === true` → 真在跑。两个 surface 都接同一份 `jobOf` 判据。

## 二、已定：「在跑」怎么常驻展示（选型 A）

一张 run 表其实早就存在（`jobs` 账本），但**只有 agent 能问**（`job list` 工具）。人看不见，
只能等模型想起来调一次。所以这轮先补出口：`diy2.jobs.list` / `diy2.jobs.kill`（与 `job list`
/ `job kill` 同一份账本、同一套语义、同一个按进程组停的入口）。

有了数据，剩下的是「放哪、怎么展开」。五个画法并排摆在同一页上（`/job-demo.html`，
真数据 1s 轮询、停止是真调用；没作业时可切假数据看形状）：

| | 画法 | 好在 | 代价 |
|---|---|---|---|
| A | 输入框上方窄条 + 向上弹层 | 最省地方，就在"正要打字"的位置 | 浮层一移就没；作业多要滚 |
| B | 标题栏徽标 + 右侧抽屉 | 不占内容区，能同时放「在跑 + 刚结束」 | 抽屉挡对话，得手动关 |
| C | 右侧常驻「作业」列（可收起） | 多任务并行一眼看全，停止常驻 | 常吃宽度 |
| D | 右下浮动胶囊 + 弹层 | 完全不动布局 | 会盖内容，容易看不见 |
| E | 底部状态栏一条 | 与「区域开关」同一条，最不打扰 | 10px 一行，太隐性 |

初步倾向 **A 作默认**（它就是"输入框上方那一条"，与 `PendingAskBar` / `SpeakingBar` 同一个
习惯：贴着 composer、不抢内容区），**B 作为"看全量"的入口**（点窄条右端展开成抽屉）；
C / D / E 作为备选。等用户在这页上挑。

**结论（2026-11-24 用户裁）**：A —— 且不是"上方窄条"，而是**输入框大框最底下一行**的
一枚 chip（`◔ 上下文 12k` · `✦ 模型` · `◉ 作业 2 · 3m20s`），与上下文 / 模型排在一起；
悬停出简要卡、点开出半屏抽屉（= diy1 tokenwindow / 模型 / 花费那套三级披露）。已落进
`ComposerBar` + `JobsChip`（`8033b135`）。

**再补一条（同日用户裁）**：作业跑完**只失去「在动」，不失去位置**——chip 常驻，0 条在跑时
退化成空状态 `◔ 作业`（灰点、不跳、不写数字与时长）。理由：它同时是**进历史账本的入口**，
跟着消失就等于把历史藏了（第一版正是 `return null`）。

## 三、顺序

1. ✅ 内联卡片（JobCard v2）+ `jobs.list` / `jobs.kill` / `jobs.tail` 出口
2. ✅ 用户选了 A，已搬进 entity-chat（`ComposerBar` + `JobsChip` 三级披露）
3. ✅ chip 常驻（0 条在跑 = 空状态，不做 `return null`）
4. ⏳ `job-done` 事件要能推（现在靠轮询：在跑 1.2s / 闲 5s）—— 候选是复用 room 流的 notify，
   或加一条 `jobs` 的 server-stream

## 四、已知边界

- `jobs.list` 目前是**实例全量**（一个实例一张表），没有按房间过滤：多任务并行时会看到
  别的任务起的作业。要不要收窄，取决于最终选哪种画法（C 更在乎这件事）。
- 轮询是权宜：真正落地时要么走事件推送，要么把轮询限在「面板展开时」。
