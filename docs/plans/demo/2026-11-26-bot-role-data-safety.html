机器人固定为「类型模板」后：数据结构 & 生产迁移安全

回答两个问题：① 机器人改成类型级模板后数据长什么样；② 换到这套结构时，生产库的会话 / 历史会不会丢。下面所有数字来自 ~/.diy2/diy2.db（你正在用的生产库，191MB）的副本实测。

1. 为什么改：从「每房间一个 bot」到「每类型一个角色」

旧：bots 表（每房间私有）

每个房间（项目 / 任务）各建一个 bot，home_entity_id 指向它归属的房间。同一个任务类型在 N 个房间里就有 N 个 bot，配置各改各的。

-- 旧表 bots
id            TEXT PK
name          TEXT
color         TEXT
persona       TEXT
home_entity_id TEXT   ← 归属房间
home_dir      TEXT
model_key     TEXT
新：bot_roles 表（每类型固定席位）

按类型（项目 / 任务）固定几个预制角色，所有该类房间共用。改一处，全类型生效。

-- 新表 bot_roles
id              TEXT PK
type            TEXT   ← project / task
name            TEXT
color           TEXT
instructions    TEXT   ← 人格（原 persona）
primary_flag    INTEGER ← 每类型至多 1
model_key       TEXT
reasoning_effort TEXT  ← 新增：推理强度
created_at      INTEGER
updated_at      INTEGER
关键约束：CREATE UNIQUE INDEX bot_roles_primary ON bot_roles(type) WHERE primary_flag = 1 —— 「每类型至多一个 primary（默认应答）」由数据库保证，不靠应用层自觉。

2. 会话 / 历史怎么挂：与 bot 解耦，所以换 bot 不影响历史

三张表各管一件事，只有会话表引用角色，历史表按房间存、与 bot 无关：

session_state
会话键 = （容器 entity_id, 角色 bot_role_id）。一个房间 × 一个角色 = 一份会话快照（turn / entries / usage）。
room_entries
房间的消息历史，按 entity_id + seq 存。不含 bot 字段 —— 换谁应答都读同一份历史。
room_members
房间 → 成员（角色 id）的对应，由角色按类型派生（membersOfType）。
-- session_state（会话键 = 容器 + 角色）
PRIMARY KEY (entity_id, bot_role_id)   ← 2026-11-24 从 bot_id 改名

-- room_entries（消息历史，与 bot 无关）
(entity_id, seq, at, entry)  ← 按房间+序号，无 bot 字段
这回答了「换机器人会不会破坏历史」：历史（room_entries）按房间存，跟 bot 是谁没关系；会话（session_state）按「房间 × 角色」存。所以「所有任务共用一个角色」= 每个任务房间各有一份「本房间 × 该任务角色」的会话，互不干扰，也不会因为合并角色而丢。

3. 生产迁移做了什么（打开新代码自动跑一次，幂等）

旧库有 bots 表→ 按 type + persona 分组折叠→ 写 bot_roles→ 会话/投递 old→new id 重写→ bots 改名 bots_v0 留档
  • 分组键 = type + persona：同类型、同人格的 bot 折成一个角色（id 取组内第一个）。
  • primary：组内在 room_members 当过 primary 次数最多的那组，平手取最早。
  • 会话重写：UPDATE session_state SET bot_role_id = ? WHERE bot_role_id = ?，old bot id → new 角色 id。
  • 历史消息作者重写（关键）：entity_items 里消息的 author.id 也按 old→new 改。界面按「消息 author.id ∈ 当前成员」决定显示，不重写就会被合并掉的旧 bot 的消息整段消失（数据在库里、只是看不见）—— 2026-11-26 实测踩到并已修，同批还重写了 asks.owner。
  • 撞键处理：同一容器里两个 bot 合并成同一角色时，只留 turn 大的那份快照，丢的份数打日志（[bot-role] 合并会话：…）。
  • 旧表不删：bots 改名 bots_v0 原样留档（同 rooms_v0 的路数）。
  • 幂等：migrateBots 开头检查 bots 表是否存在，已迁移（只剩 bots_v0）就直接返回，不会重跑。

5. 你可能担心的几点

Q：合并角色会不会把两个任务的会话混在一起？
不会。会话键是「房间 × 角色」，同一角色在不同房间各有一份独立会话。合并的是「同类型的多个 bot 定义」，不是「不同房间的会话」——每个房间的会话仍按自己的 entity_id 独立存在。
Q：撞键丢的会话是哪些？
只有「同一个房间、两个旧 bot 都被折进同一个角色」时才会撞键（同房间同角色只能有一份快照）。这种情况留 turn 大的（聊得多的那份），并打日志。真库实测没有触发（39 份会话零丢弃）。
Q：想回退怎么办？
bots_v0 原样保留 41 行旧定义，session_state 只是改列值、没删行。真要回退，从 bots_v0 可重建。迁移本身在事务里跑（BEGIN IMMEDIATE … COMMIT），中途失败整体 ROLLBACK。
一句话：机器人从「每房间私有」变成「每类型模板」，是定义层的折叠；数据层（会话、历史）按「房间 × 角色」存。折叠时要连历史消息里的作者 id一起改（否则数据在、界面看不见）—— 这个隐患实测发现并已修，修后新会话打开历史消息正常显示。
