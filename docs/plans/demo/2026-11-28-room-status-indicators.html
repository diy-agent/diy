结论

是复杂了 —— 但复杂在「事实」，不在「标题栏」

下面的词典列了 8 行，那是 数据层：这些事实确实不同，不能合并存储（合并了就分不清「消息没送到」和「跑了但报错」）。 真正的病是让每个事实都在标题栏露一次脸：3 个层次（房间 / 席位 / 轮次）× 7 个事实 × 3 处露面 = 21 格，人一个都记不住。

一条判据压到底：它出现时，我会停下手里的事吗？

会不会停手那些事实标题栏怎么放
会等你回答 / 上一轮出错 / 未送达一个数：要你 N（点开分组，组内再分「要回答」和「出错了」）
不会，但想知道在跑 / 排队一个数：在动 M（这两个本来就会互相转换，没必要分开）
连知道都不必未读 / 空闲不进标题栏（未读本来就在侧栏那一行有蓝点）

所以：数据保留 7 个事实，标题栏只留 2 个数。下面第一个方案（S0）就是这个形态，其余五个是「再多给一点表现力」的可选项。

回答什么问题

「要不要停下手里的事」—— 一个数字就能回答

适用量级

任意。两个数字永远不会爆版，也不随房间数增长

代价

丢掉「在跑 vs 排队」「出错 vs 未送达」这些细分 —— 想看就点开（那才是详情该待的地方）

现实对照：现在 #636 里的「状态 N」把在跑也算进 needsYou，于是数字=在跑+等你+出错 —— 把「要我管」和「它在忙」混成一个数，这正是复杂感的源头。

词典

一个 room 可能"是什么状态"，每个状态对你说什么

状态 从 room 看，它是什么意思 谁在等 真源（唯一一份） 要你做什么 / 会自己消失吗
上一轮出错 这个房间某个成员的最后一轮结局不是「正常结束」：被打断 / 上游超时 / 撞步数上限 / 工具结果没回来 / 被内容策略拦截 / 送不进去 你（判断要不要重来） 轮级事实 + turnLookup（与侧栏红图标同源） 要你动手：点进去看错误条，然后「继续」或改配置。不会自己消失（下一轮正常结束才覆盖）
等你回答 有张 ask 卡片挂着：模型问了个问题，选了才算完。不阻塞 —— 它那一轮早就结束了 你（选一个选项） asks 表里 state=pending 的那几条 要你动手：答 / 撤回 / 等它过期。不会自己消失
在跑 这个房间有成员正在处理某条消息（属于 working 投递），或者正被 steer 注入下一段 没人等你 —— 它自己会接着干 session.busy（内存态，全实例活动流推给你） 不用你管。会自己消失（这一轮跑完就灭）
排队（没人接） 已发出、还没有任何成员开始处理的投递条数。消息已经落库了，只是还没轮到它 消息在等（等你前面那轮跑完，或等进程把它捡起来） deliveries 里 state=pending 的行，按房间/成员计数 不用你动手，但可以什么都不做地看它走。会自己消失：成员取到它 → 这条变 working（此时该席位显示「在跑」，排队数 −1）
未读 已经有新结果、而你还没看（seq 超过已读水位，且不是我自己发的） 你（去看看吧） room_read 的已读水位 要你看一眼。打开房间即清（只前进不后退）
未送达 这个房间最新一条消息没交到成员手里：deliveries 那行落成 state=done, note='failed'。历史失败不算 —— 后来的新消息送达了就翻篇 你（重发那条 / 看是不是数据被清） deliveries 表按 (房间, 成员) 收敛到最新一条（轮次 → 消息 seq → 时间 → messageId 依次比） 要你动手。不会自己消失（下一条正常送达才盖掉）
空闲 上面这些一个都没有：上次正常说完、现在没动 没人 以上皆为 0 / 空 不用你管
关闭（任务） 任务本身 status=closed。它和上面那些正交：关掉的任务也可能有未读、出错 — room.data.status（UI 的 isClosed() 唯一真源） 要你重开或忽略
「排队」到底是什么 —— 三条别搞混
  1. 它不是「房间在一个队列里等名额」：diy2 没有房间级队列、没有并发闸门。排队的是消息，单位是「这条消息还没被哪个成员接走」。
  2. 它和「在跑」可以同时存在：同一个房间，成员 A 正在跑上一轮（working）→ 你刚发的两条还是 pending。所以 room 级的「排队 N」是附带信息，不是第 5 种互斥状态。
  3. 「只有排队、没人跑」才值得看：正常情况下一秒就变成在跑；如果它停在那儿不动，说明没人接（进程刚重启、成员被堵、投递反复失败）—— 这时候它是琥珀色警告，不是绿色呼吸。
先直觉理解：它是「这句永远没人读到」的墓碑

一条消息发出去，系统会在 deliveries 里给它记账（每个成员一行）。正常路径是 pending（排队）→ working（有人接了）→ done（读完了）。 「未送达」= 这条账走到头了，但不是被读完结束的，而是放弃了：done + note='failed'。 所以它跟「跑失败了」不是一件事 —— 那是「读到了、跑了、结果不好」，这是「根本没读到」。

一次真实的「未送达」长这样：

  1. 你发了一条消息 → 房间里 3 个成员各一行 pending
  2. 两个成员秒接 → working → done；第三个还没轮到，还是 pending
  3. 这时进程被 kill / 机器重启
  4. 重启后 room.recover() 逐条重投：拿出第三条 pending，去库里取它的正文（store.textOf()）
  5. 取不到（正文被裁剪 / 已不在最近那批条目里）→ 无从投递 → 直接写 done + note='failed'
  6. 结果：时间线上有你这句话，但永远不会有第三个成员回复；侧栏那一行挂一颗红叉

另一条路更少见：想用 steer 把话插进正在跑的那一轮，插不进去、且配置不允许顺延到下一轮 —— 这句既没进这一轮、也没进下一轮，同样标成「未送达」。

为什么它不会自己好：系统没有「正文丢了还能重发」的能力（丢的就是正文）， 所以它只能记账 + 亮红叉，把决定权交回给你：把那句重发一遍（或去查为什么会被裁掉）。 也正因为不会自己好，它和「排队」（会自己消失）必须分开显示。

⚠ 已知脆弱点（诚实标注）：textOf() 只扫「最近 200 条条目」。 如果那条 pending 投递对应的消息已经被挤出这 200 条（同房间后来产出很多）， 恢复时同样会「取不到正文」→ 被标成未送达 —— 但正文其实还在库里。 也就是说当前实现里「未送达」混了两件事：真的没送到（steer 插不进）和 只是没查到（200 条窗口）。后者属于 bug，不该叫这个名字。

「未送达」是「投递层」的失败，不是模型失败 —— 代码里只有两处会写它
失败在哪层真源典型来路会自己消失吗
未送达（投递层） deliveries 里那条 done + note='failed' ① recover() 时这条 pending 投递的消息正文在库里找不到了（被剪 / 被删）→ 无从投递；
② 想用 steer 插进正在跑的那一轮，插不进去且不允许降级成下一轮		 下一条消息正常送达就翻篇（按成员取最新一条）
上一轮出错（轮次层） 轮级事实 + turnLookup 的 outcome 模型报错 / 被打断 / 步数上限 / 工具失败 / 被拦截 —— 消息它拿到了、也确实跑了 下一轮正常结束才覆盖

反过来说：模型调用报错不算未送达 —— 那条消息已经进了 bot 的上下文，只是这一轮结局是 failed； 它落在「上一轮出错」那一档（postOrWarn 的 catch 只记一行日志，不改投递状态）。 而投递失败才是「你说了话、没人读到」：所以它单独一颗红叉 ✕，不混进「排队」（那条是「马上要动」）。

所以标题栏的口径：值得催你的只有三档 —— 上一轮出错 / 等你回答 / 排队却没人接； 在跑是「它自己会好」，未读是「你自己会去看」。后两者不该在标题栏争位置（也不该进红点）。

怎么选：三个问题定方案

你的判断选它理由
先问「要不要停下来」—— 任何量级都适用S0两个数；细分全进点开的面板。先把这层做对，再谈表现力
房间长期 > 20 个，标题栏只想看「有没有事」S1 + S5计数不随房间数膨胀；底边条给构成感
同时压着的事通常 ≤ 3 件，人只关心「先做哪个」S3少即是多：把唯一该动手的摆出来，其余折叠
要「一眼看到是哪个任务在等我」S4只有它在标题栏里放得下名字
房间少（< 10）且互相独立，喜欢看整体节奏S2点阵的密度感最强，且天然支持「最近 N 个」
真正的战场是侧栏，标题栏只在有急事时出声S6不给标题栏加负担，靠行内徽标说话

可以组合，但别叠三层：S3（主）+ S1（次）+ S5（底边） 是密度与可读性最稳的一套； S4 + S6 会重复（都在说「哪个房间」）。真正要避免的是现在这种——两个纯数字，既不说是谁，也不说该干什么。

假数据 · 无后端 · 单文件。主状态取最急一档（同房间多件事并存时按 出错 > 等你回答 > 在跑 > 没人接 > 空闲）； 排队 与 未读 是附带标记，不参与排序 —— 它们能与「在跑」同时成立。
