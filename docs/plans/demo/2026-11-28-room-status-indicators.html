room 级状态指示器：6 个候选形态

现在的标题栏只有两串数字（Bot N / 状态 N）—— 能说出「有几个」，说不出「是哪个、要我干什么」。 下面每个方案都是**同一份假数据**的渲染，切上面的房间数看它在 4 / 12 / 40 个房间下怎么退化。

房间数
最急优先：出错 → 等你回答 → 在跑 → 排队 → 未读 → 空闲
上一轮出错 等你回答 在跑 排队 未读 空闲
S1

分档胶囊：按「最急状态」分组计数

有几件事要处理？· 点一档看是哪些房间
diy2 · 切片
回答什么问题

「现在总共压着几件事、分别是哪一档」

适用量级

任意。房间再多也只是一排数字，不会爆版

代价

只说类别不说名字 —— 想知道是哪个还得点开一次

业界：VS Code 状态栏、GitHub Actions 概览、Slack 侧栏分组红点。

S2

状态点阵：一个房间一格

整台实例的「体温」· 悬停看是哪个房间
diy2 · 切片
回答什么问题

「整体忙不忙、有没有几个红的挤在一起」

适用量级

≤ 24 格清晰；再多要按状态聚合或分页（+N）

代价

格子太窄放不下名字；同色多格看不出谁是谁，必须悬停

业界：GitHub 贡献图、Datadog 服务网格、CI 的 workflow 结果点阵、Linear 的 cycle 进度点。

S3

最急一件 + 队尾计数（attention first）

直接把该做的那件事摆出来 · ‹ › 换下一件
diy2 · 切片
回答什么问题

「现在最该我动手的是哪一件、它要什么」

适用量级

任意。房间越多越占优 —— 你不需要知道另外 37 个

代价

一次只推一件；总量靠「+N」暗示，看不清全局分布

业界：Linear Inbox、Things 的 Today、PagerDuty「worst first」、iOS 通知摘要。

S4

横向 chip 带：带名字的流水

谁在等你，一眼读出房间名
diy2 · 切片
回答什么问题

「哪几个房间在等我，分别等什么」

适用量级

≤ 4 个正好；再多横向滚动（滚出视野 = 看不见）

代价

占标题栏宽度，与区域开关抢地方；名字长就截断

业界：Slack 顶部未读条、Teams 活动、Discord 私信徽标、Jira「我的待办」。

S5

状态条：标题栏底边一条彩色分段

零宽度成本的全局条形图 · 悬停看段
diy2 · 切片
回答什么问题

「全局构成：多少比例是红的/蓝的/绿的」

适用量级

≤ 12 段可分辨；更多要按状态合并成几段

代价

2px 高，单段无法点中；只能当提示，不能当入口

业界：VS Code 编辑器 tab 的脏标记、JetBrains 底部进度条、macOS Dock 徽标、浏览器 tab 的忙碌转圈。

S6

侧栏为主 + 标题栏只留一颗「最坏的」

room 级信息回到「能看见名字」的地方
diy2 · 切片
回答什么问题

「每个房间自己什么状态」—— 逐行看，不用去标题栏换算

适用量级

任意：侧栏本来就要滚动，状态跟着行走

代价

跨房间总览弱：要扫一遍列表才知道全貌（标题栏退化成一粒灯）

业界：Slack（侧栏才是主战场）、Notion、VS Code 资源管理器的 git 色、Finder 侧栏徽标。

↔

怎么选：三个问题定方案

你的判断选它理由
房间长期 > 20 个，标题栏只想看「有没有事」S1 + S5计数不随房间数膨胀；底边条给构成感
同时压着的事通常 ≤ 3 件，人只关心「先做哪个」S3少即是多：把唯一该动手的摆出来，其余折叠
要「一眼看到是哪个任务在等我」S4只有它在标题栏里放得下名字
房间少（< 10）且互相独立，喜欢看整体节奏S2点阵的密度感最强，且天然支持「最近 N 天」
真正的战场是侧栏，标题栏只在有急事时出声S6不给标题栏加负担，靠行内徽标说话

可以组合，但别叠三层：S3（主）+ S1（次）+ S5（底边） 是密度与可读性最稳的一套； S4 + S6 会重复（都在说「哪个房间」）。真正要避免的是现在这种——两个纯数字，既不说是谁，也不说该干什么。

假数据 · 无后端 · 单文件。状态口径沿用 BotRow：出错 > 等你回答 > 在跑 > 排队 > 未读 > 空闲 （同一房间取最急的那一档）。颜色用 DESIGN.md 的语义四档 + 未读蓝。
