bot 与 session 的领域模型：当前实现 vs 目标模型

你的模型：bot 就是一个连续无截止的 session；任务是模块贡献的人设（代码概念、不存储、无 id），建任务时自动产生一个 mainbot、不能换；room 默认单聊；会议 = 新容器放公共记录、各 bot 仍用原 session。下面是当前代码逐条对照。

结论：有显著出入，而且是结构性的。当前是「type 级全局角色 + per(房间,角色) session」；你要的是「per-task bot（=连续 session）+ 代码贡献点人设 + 会议用原 session」。核心差 3 处（bot 粒度、session 键、人设存储）。

3. 三个核心出入（详解）

① bot 是 type 级全局角色，不是 per-task 实例

现在 BotRole 带 type: 'task'，所有 task 房间的成员都由 membersOfType(roles, 'task') 派生 —— 同一个「任务助手」服务所有任务。你要的是每个任务创建时产生一个自己的 mainbot（像「小满」属于某个任务，不是所有任务的）。

// 现在：一个角色服务所有 task 房间
task-mwjddcy0 → members: [任务助手(bot-mwh80b5n), ...]
task-mwlxxv3u → members: [任务助手(bot-mwh80b5n), ...]  ← 同一个 id

② session 是 per(房间,角色)，不是 per bot 连续

主键 (entity_id, bot_role_id) 意味着同一角色在不同房间各有一份 session。你的「会议用原 session 保记忆」要求 session 跟着 bot 走、跨 room 连续 —— 当前做不到（换 room 就是新 session）。

// 现在：session 绑房间，不绑 bot
session_state[task-A, 任务助手] = 会话1   ← 同一 bot
session_state[task-B, 任务助手] = 会话2   ← 两份，记忆不连
// 你要：session 绑 bot，跨 room 一份
session[bot-任务A的mainbot] = 连续会话  ← 会议也用这份

③ 人设存在表里，不是代码贡献点

你要的是：任务模块代码里定义一个「mainbot 人设贡献点」，不存储、无 id；建任务时用系统默认模型自动创建 bot；只有人设要单独配模型时才存。当前是 bot_roles 表存了 id/name/instructions —— 这是最根本的差异：人设从「表记录」变成「代码里的贡献点」。

// 你要的形状（示意）
taskModule.contributeBot({
  role: 'main',              // 人设概念，不是名字
  persona: '任务视角：做完要能自己验',
  // 不配 model → 用系统默认模型，不落库
})
// 建任务时：bot = { id: 自动生成, task: task-A, personaRef: taskModule.main, model: null }

4. 能适配吗？分三块，从易到难

  • 第 1 块（中等，收益最大）：session 键改 per bot。session_state 主键改 (bot_id)，room_entries 仍按 room 存公共记录。这样「会议用原 session 保记忆」自然成立，也是「bot = 连续 session」的落点。不动 bot 粒度和人设存储，风险可控。
  • 第 2 块（较大）：bot 改 per-task 创建。任务创建时建一个 bot 记录（bot_id + task_id + 可选模型覆盖），而不是 seed 全局角色。房间成员从「派生」改为「显式绑定」（任务 room 绑自己的 mainbot；会议 room 绑拉进来的几个）。
  • 第 3 块（最根本）：人设改代码贡献点。人设不存表，任务模块代码里定义贡献点；bot 记录只存「哪个贡献点 + 可选模型覆盖」。这样「没任务就没 bot、无数据库级人设」成立。这要动任务模块的贡献机制和 seed。
为什么建议先做第 1 块：「记忆连续」是这套模型最核心的承诺，而它只取决于 session 键；bot 粒度和人设存储是「谁是谁」的组织方式，改起来牵动任务模块和 seed，风险高。先改 session 键能立刻验证「会议/跨 room 记忆」这个核心体验。

5. 待你拍板

方向：① 先只改 session 键为 per bot（试水，风险可控）；② 按目标模型整体重构（per-task bot + 代码贡献点人设 + per-bot session）；③ 先保持现状、只留这份分析。
若整体重构，一个关键点：人设是否真的「不存表」？如果人设完全代码贡献、无 id，那「单独给人设配模型」就落在 bot 记录（per-task）上，而不是人设上 —— 需要确认这个归属。
