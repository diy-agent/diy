# 实体身份与域表（entities / tasks / projects）

> 2026-11-21 · 任务 ##实体迁移 · 用户决策：任务独立成域、项目降级为字段、插件数据归插件。

## 0. 一句话

**身份一张表，存储分域，插件不进来。** `entities` 只回答「是谁」，`tasks` / `projects` 是真源，
插件实体只有身份行、payload 在自己那儿。`Room` 退化成给旧 UI 看的投影。

## 1. 三条不变量

1. **一切可被引用的东西在 `entities` 里有一行**（core：project / task / bot；插件：`<包名>/<局部名>`）。
   没有这一行，就不能出现在 `entity_links` / 事件 `subject` 里。
2. **插件不写我们的表**。`entities` 之外一行都没有；数据放 `~/.diy/plugins/<plugin_id>/`。
3. **编号不回收**。`counters.next` 独立于任务行，删任务不影响下一个号；改项目 / 改目录也不换号。

## 2. ID 规则

| 项 | 规则 |
|---|---|
| 新实体 | UUIDv7（RFC 9562），小写 36 字符，无前缀 |
| 旧实体 | **不重写**（`proj:diy` / `task-mwj3x9` 原样保留 —— 它们挂着消息、会话、日志） |
| 构造入口 | `newEntityId(now?)`；同毫秒内单调（顺序位），时钟回拨不倒退 |
| 校验 | `isEntityId()` 只在「这里该发新 id」的入口用 |
| 不做 | branded type（`string & {[brand]}` 在 sqlite / http / jsonl 边界全丢，`as` 恰好跳过校验） |

## 3. 类型规则

```
core    project / task / bot            ← 闭合集合（CORE_TYPES）
plugin  <npm 包名>/<局部名>              ← @acme/github/issue、x/issue
```

- 判据：含 `@` 或 `/` ⇒ 插件；否则 core。
- 解析靠 npm 名字形状：`@scope/name` 恰好一个 `/`，裸名没有 `/` ⇒ 反解无歧义（`splitPluginType`）。
- 局部名 `^[a-z][a-z0-9_-]*$`（不含 `.` `/` `@`），这样事件名 `x/issue.synced`、引用串
  `x/issue:<uuid>` 都能用 `lastIndexOf` 切开。
- 明确不做：`agent.run` / `agent.turn` / `agent.step` 不是实体（它们是 `session_state` 的列）。

## 4. 表结构

```sql
PRAGMA foreign_keys = ON;

-- 身份：不存业务字段
CREATE TABLE entities (
  id         TEXT PRIMARY KEY,
  type       TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE INDEX entities_type ON entities(type);

-- 任务域（真源）
CREATE TABLE tasks (
  id         TEXT PRIMARY KEY REFERENCES entities(id) ON DELETE CASCADE,
  number     INTEGER NOT NULL UNIQUE,
  title      TEXT NOT NULL,
  summary    TEXT NOT NULL DEFAULT '',   -- 一句话描述（旧 Room.data.desc）
  body       TEXT NOT NULL DEFAULT '',   -- 正文（旧 Room.data.body）
  project_id TEXT,                       -- **只是字段**，不做外键（删项目留孤儿，侧栏有 orphans）
  workspace  TEXT,                       -- 工具 cwd，与项目解耦
  status     TEXT NOT NULL DEFAULT 'open',
  closed_at  INTEGER,
  model_key  TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE INDEX tasks_project ON tasks(project_id, status, id);

-- 项目域（真源）：没有任何 tasks 子目录
CREATE TABLE projects (
  id        TEXT PRIMARY KEY REFERENCES entities(id) ON DELETE CASCADE,
  name      TEXT NOT NULL,
  workspace TEXT,
  model_key TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

-- 编号：next = 下一个要发的号（删任务不回收）
CREATE TABLE counters (scope TEXT PRIMARY KEY, next INTEGER NOT NULL);
```

记录表（`entity_items` / `room_entries` / `session_state` / `deliveries` / `drafts` /
`journal_entries`）**不在此列**：它们属于某个实体、没有独立身份、不参与引用。
`deleteRoom` 先删记录，最后删 `entities` 一行（域行随 `ON DELETE CASCADE`）。

## 5. Room 兼容层（本阶段的过渡）

`apps/diy2/server` 与 entity-chat 仍以 `Room`（`{id,type,name,data,members,modelKey}`）为线上形状。
store 做双向映射：

| 域列 | Room 里的键 |
|---|---|
| `tasks.title` | `data.title`（只有**项目**的名字是 `data.name`） |
| `tasks.summary` | `data.desc` |
| `tasks.body` | `data.body` |
| `tasks.project_id` | `data.projectId` |
| `tasks.workspace` | `data.dir` |
| `tasks.status` / `closed_at` | `data.status` / `data.closedAt` |
| `projects.workspace` | `data.dir` |
| `tasks.number` | `data.number` —— **只读派生**（`counters` 落库时才发号） |
| `tasks.created_at` | `data.taskDir` —— **只读派生**（`<数据根>/tasks/<日期>/<id>`，不落库） |

「只读派生」两列是**映射的例外**：进得去（`taskToRoom` 写）、出不来（`roomToTask` 不读，调用方自己填也没用）。
所以内存那份手写的 `Room` 里它们一开始是**没有的** —— server 落库之后必须抄回来（`apps/diy2/server/app.ts`
的 `adoptDerived`），否则本次运行期间 `rooms.list` 给出的任务缺 `#号` / 「任务目录」，重启才补上。

映射是**单向闭集**：`data` 里别的键既不读也不写（老库残留的 `parent` 之类会在下次保存时消失）。
`saveRoom` 只接受 `project` / `task`，其它类型抛错（core 容器只有这两类）。

新代码用 `saveTask` / `saveProject` / `listTasks` / `taskOf` / `listProjects` / `projectOf` / `entityOf`；
Room 接口在 UI 迁移完成后删除。

## 6. 老库迁移（`rooms` → `entities` + 域表）

- 逐行 upsert（**幂等**）：编号沿用已有行，`created_at` 保持原值。
- 状态归一：`todo` / `doing` → `open`，`done` → `closed`；未知值原样保留。
- `data` 里的 `desc` / `body` / `dir` / `projectId` / `closedAt` 落进真列；`data` 坏 JSON → 空袋，不拦迁移。
- 全部成功后才 `ALTER TABLE rooms RENAME TO rooms_v0`（留档，确认无误后可手动删）。
- 迁移后 `counters.next = MAX(number) + 1`。

## 8. 与外部规范的差异（有意的）| 外部提法 | 本文档 | 原因 |
|---|---|---|
| branded type | 不做 | 跨边界丢失，`as` 绕过校验 |
| `agent.run/turn/step` 实体 | 不做 | 会话内部结构，不是可引用对象 |
| Turn/Step 的全局 UUID | 不做 | 量巨大且无需跨实例引用 |
| `npm:` 前缀 + `#` 分类型 | `@acme/github/issue` | `:` / `#` 与引用串、事件名冲突 |
| publisher / scope 字段 | 不做 | 只是 npm 名字的可选前缀，不是独立概念 |
| `plugin_id` 取首次安装地址 | 取包名（作者声明） | 发布源会变，身份不该变 |
| Number 多作用域 | 只有 task / instance | 任务跨 workspace、无目录层级 |
| `entities.data` JSON 袋 | 分域真列 | 开放袋子无法回答「字段属于谁」 |

## 9. 任务目录（P2 已定）

```
<数据根>/tasks/2026-11-21/<taskId>/
```

- **按创建日分桶，之后永不移动**（改项目 / 改状态 / 改 workspace 都不搬目录）。
- **平铺日期段**而不是 `YYYY/MM/DD`：最后一级都是「当日任务数」，扇出相同；平铺路径短、
  一年 365 个目录一眼可浏览，且 `rm -rf tasks/2025-*` 同样能做归档。
- 三层只在「按月物理分区」（打包 / 挂载 / 配额）时才划算，diy2 现在不需要。

实现（`src/task-dir.ts`）：

| 文件 | 谁写 | 说明 |
|---|---|---|
| `task.md` | 每次内容变化时原子重写 | frontmatter + 正文；**DB 才是真源**，手改会被覆盖 |
| `journal.jsonl` | `appendJournal` 追加 | 一行一条 `{seq,at,kind,text}` |
| `artifacts/` | 空目录先建好 | 截图 / 日志等产物 |

- 路径由 `(createdAt, id)` 推出，不存列、不迁移；目录名里的 `:` 换成 `-`（Windows 非法字符）。
- 删任务把整个目录挪进 `tasks/_trash/<日期>-<id>`，**不删产物**。
- 写文件失败只打日志，不影响 DB（磁盘满不该让任务存不下去）。
- `tasks.updated_at` 只在内容真的变化时盖章（启动时全量重存不算）。

## 10. 插件注册表（P3）：运行时模型，不是表

**结论：不建 `plugins` 表。** 注册表是启动时加载清单（JSON）得到的**内存模型**：

```
package.json（含 diy 段）  →  加载/校验  →  PluginRegistry（Map<plugin_id, Plugin>）
```

现有实现已经这么做了：`pkgs.ts/ui/workbench-dock/examples/03-plugin/registry.ts::loadPlugins()`
吃 `PluginPackage[]`（清单 + 组件），吐 `Contribution[]`；清单写错在**加载时**炸（不是运行时白屏）。
并且它本来就把 `manifest.name` 当 `pluginId` —— 与本文档「包名即身份」一致。

需要修的冲突：

| 现状（已修） | 冲突 | 定夺（已落地） |
|---|---|---|
| `workbench-plugin/manifest.ts` 用独立 `plugin.json` + `id` 短 slug | 与「包名即身份」冲突，且装不下 `@scope/name` | 身份 = `package.json.name`；`id` 已删 |
| 清单里没有实体类型声明 | 插件实体无法注册 | `diy.entityTypes: [{name, schemaVersion}]`，全名 = `<name>/<local>` |
| 两个清单形状并存（`plugin.json` vs `package.json.contributes`） | 加载器要认两套 | 统一成 `package.json` 的 `diy` 段；`contributes` 由宿主自解释 |

实现：`workbench-plugin/src/{manifest,registry}.ts`（`createPluginRegistry`，纯函数 + 加载期校验：
插件 id 重复 / 实体类型重复 / apiVersion 不支持一律抛）。

`entities` 里仍然会有插件实体的**身份行**（可被引用、可进关系/事件），但「装了哪些插件」
来自运行时加载结果，不来自数据库。将来真要记录安装来源，用 `<数据根>/plugins.json`
（`{id, source, version}`）即可 —— 仍然不是表。
