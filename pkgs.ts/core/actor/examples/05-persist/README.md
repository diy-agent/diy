# 05 — 崩溃恢复：一次提交 = 一行

**这一节只讲一件事：状态和游标写在同一次 `append` 里，所以「崩在中间」只有两种可能 —— 那一行没有，或那一行完整。**

## 跑

```bash
./sha.sh e05
```

## 输出

```
  （启动时恢复：seq=0，0 条消息）
  （启动时恢复：seq=2，2 条消息）
重启后第一条 → seq=3（不是 1）
恢复出来的日志：1.一 2.二 3.三

  （启动时恢复：seq=3，3 条消息）
崩溃后重启看到的条数：3（那条没落盘的凭空消失）
日志：1.一 2.二 3.三

文件里最后两行（一行一次提交，没有半截状态）：
  {"lines":[...两条...],"seq":2}
  {"lines":[...三条...],"seq":3}
```

## 关键点：一行 = 一整个状态

```ts
await appendFile(store, JSON.stringify(state) + '\n');
```

`state` 里同时有 `lines` 和 `seq`。它们要么一起落盘，要么一起没落。

所以恢复只需要读**最后一行**：

```ts
const last = raw.trim().split('\n').filter(Boolean).at(-1);
return last ? JSON.parse(last) : { lines: [], seq: 0 };
```

不存在「消息写了、序号没走」这种半截状态 —— 因为从来没有分成两次写。

## 第三段在证伪什么

`_pushWithoutSave` 把一条 `seq: 999` 推进内存、**不 append**，然后关掉进程。重启后：

```
崩溃后重启看到的条数：3（那条没落盘的凭空消失）
日志：1.一 2.二 3.三
```

那一条**凭空消失**，而不是变成一个孤儿（比如「有第 999 条但没有 1~998」）。这是因为内存状态本来就不是真相，落盘的最后一行才是。

## 这不是「持久化框架」

整个存储层就是 4 个函数：

| 函数 | 行数 |
|---|---|
| `load()` | 4 |
| `openRoom()` | 20 |
| `appendFile` 那一行 | 1 |
| 关掉时的清理 | 1 |

**JSONL 追加 + 读最后一行**，就这两件事。没有事务、没有 WAL、没有快照格式、没有迁移。

什么时候它会不够用：文件无限增长时（需要 compaction，加一个「每 N 条写一次全量快照」就行）。

## 和 04 的关系

04 讲「中断时保留已产出的部分」，05 讲「崩溃时回到最后一个完整提交」。两者合起来才是「进程随时可能死」的完整答案：

- 正常取消 → 返回值带着已产出的部分
- 进程崩溃 → 回到最后一行完整的提交
