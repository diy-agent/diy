# 03 — 连点三次 = 三个工作单元

**这一节只讲一件事：用户连点 N 次，就按点击顺序跑 N 次，一次一个。UI 不用禁用按钮，也不用自己写队列。**

## 跑

```bash
./sha.sh e03
```

## 输出

```
不排队的三次：
  你: 一
  agent: 回复（发出时看到 0 条历史）
  你: 二
  agent: 回复（发出时看到 0 条历史）
  你: 三
  agent: 回复（发出时看到 0 条历史）
  ↑ 三个 turn 都以为自己看到 0 条历史 —— 前面两次的回复它们都没看见

排队后的三次：
  #1 → 回复（发出时看到 1 条历史）
  #2 → 回复（发出时看到 3 条历史）
  #3 → 回复（发出时看到 5 条历史）
```

## 读「看到几条历史」这一列

- 不排队：`0 / 0 / 0` —— 三个 turn 同时读到空历史，各自回了一句，最后 transcript 里三条回复互不知情。
- 排队：`1 / 3 / 5` —— 每次 turn 开始时，前面所有 turn 的「你说 + agent 回」都已经在里面了。

这就是「连点三次」要的行为。**顺序由投递顺序决定，与完成先后无关。**

## UI 侧

调用方代码：

```ts
const [a, b, c] = await Promise.all([room.say('一'), room.say('二'), room.say('三')]);
```

三个调用并发发出，一个 `await` 都不加。不需要：

- ❌ 禁用按钮
- ❌ `if (busy) return`
- ❌ 自己维护 `pending: Task[]` 数组
- ❌ 点第三次时取消前两次

## 最后一段在讲什么

```ts
const pending = room.say('四'); // 慢
const snapshot = room.transcript(); // 排在「四」后面
```

读也排队，所以 `transcript()` 拿到的是「四」跑完后的状态 —— 含刚说完的那条，不含它一半的状态。

代价：`snapshot` 要等「四」跑完才 resolve（总耗时 ≈ 40ms）。要中途看进度，只能靠回调推，见 `04-cancel`。
