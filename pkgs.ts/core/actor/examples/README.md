# 范例

每个目录只讲一件事，一个 `index.ts` + 一个 `README.md`。**按顺序看，前面的不再重复。**

```bash
./sha.sh all     # 八个一次跑完
./sha.sh e03     # 只跑第三个
```

| #   | 目录                                 | 讲什么                   | 一句话结论                                                     |
| --- | ------------------------------------ | ------------------------ | -------------------------------------------------------------- |
| 01  | [`01-serial/`](./01-serial/)         | 不排队会丢东西           | 连点三次 → `1` 而不是 `3`                                      |
| 02  | [`02-room/`](./02-room/)             | 调用即得值               | `await room.say(...)` 拿到这一次的结果，不是消息对象           |
| 03  | [`03-queue/`](./03-queue/)           | 连点 N 次 = N 个工作单元 | 顺序由投递决定，与完成先后无关；UI 不用禁用按钮                |
| 04  | [`04-cancel/`](./04-cancel/)         | 取消                     | `close()` abort；已产出的部分**正常返回**，不抛异常            |
| 05  | [`05-persist/`](./05-persist/)       | 崩溃恢复                 | 一次提交 = 一行；崩在中间只有「整行有 / 整行没有」             |
| 06  | [`06-rpc-bridge/`](./06-rpc-bridge/) | 跨进程（rpc 桥接）       | actor 一字不改；取消穿过进程边界，同一行 `life.signal.aborted` |
| 07  | [`07-aggregate/`](./07-aggregate/)   | 多个 actor 汇总          | 整体状态是一个 actor 的 state，不是「问 N 个」                 |
| 08  | [`08-cmd/`](./08-cmd/)               | 声明式（cmd）            | `cmd()` 声明的契约，`implement()` 那侧的类型自动推出来         |

## 建议的读法

**先读 01、02 就够判断这个东西值不值得用。** 03–08 是具体场景，需要哪个看哪个。

06 和 08 涉及跨进程，两者做的是同一件事，而且**都是契约与实现分居两文件**：06 手写类型和转手，08 用 `cmd()` 声明契约、`implement()` 绑实现，两边的类型一次推出来。先看 06 理解「为什么需要桥」，再看 08 看「怎么少写一半」。

两边都刻意没有把契约和实现塞进一个文件 —— 客户端要 import 契约，塞在一起会把实现（以及它依赖的 `node:fs` 之类）整棵打进客户端包。

内核（`@diy-agent/actor`）仍然零依赖；08 用的 `@diy-agent/actor/cmd` 才需要 zod + rpc。

## 每篇 README 的结构

1. 这一节只讲一件事（一句话）
2. 怎么跑
3. 实际输出（原文贴）
4. 为什么
5. 常见误解 / 代价

## 这些范例刻意不做的

它们是**可执行的说明**，不是框架。真正的产品代码要多考虑：

- 错误处理与重试边界
- 状态快照的 compaction（05 只追加不压缩）
- 断线重连（rpc 的 transport 有 `onClose`，范例里没接）
- 幂等键（重发 = 执行两次）
- 多进程写同一个文件（05 假设单写者）
